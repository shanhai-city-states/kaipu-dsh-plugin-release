## 一、★★ 一个必须先说清的前提：插件要有宿主

"客户从插件市场装插件"的前提是 —— **客户已经有一个 DSH**。三种情况：

| 客户情况 | 谁提供宿主 | 我们交付什么 |
|:--|:--|:--|
| **已有 DSH**（官方 Web / 自建部署） | 客户自己 | ★ **只交插件包**（主路径） |
| 没有 DSH，但会折腾 | 客户自己下载/自起 DSH | 插件包 + **安装引导** |
| 没有 DSH，且不懂技术 | **我们** | 才轮到 `apps/shell`（**后置**） |

⇒ **壳不是"客户端版本"，是"零门槛分发形态"。** 它的存在**不改变插件为主**这件事。

⇒ ★ 由此得出一条硬纪律：**`apps/shell` 里不得出现任何 083 业务代码**。壳只做三件事 ——
① 起窗口 ② 起 DSH 侧车（profile 随包） ③ 把 DSH 地址给 WebView。
**业务全在 `packages/plugin-*` 里。** 这条一旦破，插件就不能独立分发，整个生态入口（R1/R2/R7）全废。

## 二·补、★ 评审三处留意点的处置（2026-10-04）

### 留意 1 · `packages/contract` 与插件独立分发的关系 —— ✅ 已定并写清

**问题**：插件要上 DSH 插件市场，客户装插件时 `contract` 的依赖怎么办？

**定论**：

> ★ **`contract` 是「开发期类型契约」，不随插件分发。运行时不需要它。**

| 依据 | 说明 |
|:--|:--|
| 编译期 | `contract` 里**只有 `interface` / `type` / `const` 字面量表** —— **没有运行时逻辑**（`errors.ts` 的翻译函数会编译进调用方产物） |
| 构建期 | 类型在 `tsc` 阶段被**擦除并内联**；`const` 表被 bundler **内联进 client bundle** |
| 运行时 | 插件产物里**不存在** `@shanhai/kaipu-contract` 这个包 —— 它是 `dependencies` 里的**构建期依赖**，不是运行期依赖 |

⇒ **要做的三件事**：

| # | 动作 | 状态 |
|:-:|:--|:-:|
| 1 | 把 `@shanhai/kaipu-contract` 从 `dependencies` 移到 **`devDependencies`**（构建期依赖的正确声明） | ✅ **已做** |
| 2 | 打包产物**自带**类型与常量（bundler 内联）⇒ 插件包**零外部依赖**（只留 `@deepseek-ai/cordis` 作 `peerDependencies`） | ⏳ Step 2（要真产物才能证） |
| 3 | 加一条**分发断言**：插件 tarball 里 **grep 不到** `@shanhai/kaipu-contract` 的 import ⇒ 接进 `clean-scan` 或新增 `check-package.mjs` | ⏳ Step 2 |

★ 附带好处：**零外部依赖**是"能上插件市场"的硬条件 —— 市场不会替你解决依赖树。

### 留意 2 · `plugin-platform` 未来可能要拆 —— ✅ 已记演进方向

现在**不拆**（当前它确实是"一件事：提供场地"）。拆的触发条件与去向写在
`packages/plugin-platform/README.md` 的「**未来演进方向**」段（编排 / 门禁 / 留痕 / 报告面各自的拆分判据）。

★ 纪律：**按"触发条件"拆，不按"感觉变大了"拆** —— 没到触发条件就拆，只会多出四个包互相 import。

## 三、★ 关于"客户空间左右分栏"（003 最后那版 UI）

阿舟问过：003 最后优化的**内侧竖栏设计**（客户空间左右分栏）能不能参考？

**能，而且正是插件面板该有的形态** —— 理由：

1. **插件面板天然是"嵌在宿主里的一个区域"，不是全屏应用。** 它可能挂在**侧边栏**（很窄）、
   **主区域**（很宽）、或**悬停卡**（更窄）。**左右分栏 + 弹性伸缩**是唯一天然适配三档的布局。
2. 003 那版已经实测过"左列表 / 右工作区"在手边操作上更顺（用户当时的原话是"漂亮"）。
3. **但只抄设计，不抄代码** —— 003 那份耦合了财税业务（客户 / 任务 / 归户 / 拖拽上传），
   083 要的是**通用层**（铺子 / 场景 / Agent / 报告）。

⇒ 落到本仓：`plugin-platform` 的面板 = **左侧（场景列表 / 运行记录）+ 右侧（运行视图 / 报告）**；
**窄挂载自动折叠左栏**（断点由容器宽度决定，不由窗口宽度）。

**插件不直连模型/服务端域名**（一切走宿主适配层）· **插件不越受管根**。

### D4 · ★★ 内部包内联：client 侧产物必须是 **CJS**（2026-10-05，用一次"假的构建成功"换的）

**背景**：Step 4/6 要让面板直接用契约常量（`VERDICT_TONE` / `lampKey` / `SSE_EVENT`）。
契约层存在的唯一理由就是"这些常量只有一个出处"，所以**不能抄一份到客户端**（那是漂移）。
⇒ 只能把契约包**内联进 bundle**。

**踩到的坑（两级）**：

| 级 | 症状 | 根因 |
|:-:|:--|:--|
| 1 | 内联后产物里留着一句 `require("@shanhai/kaipu-contract")` | 宿主 closure 的 `require` 只服务宿主模块表 ⇒ 浏览器拿到 **undefined** |
| 2 | 内联进来了，但浏览器报 **`SyntaxError: Unexpected token 'export'`** ⇒ 整站不渲染 | 契约包产物是 **ESM**（`module: ESNext`），而 client bundle 是 **CJS closure** |

**★ 级 2 最难查的地方：构建是绿的。** bundle 文件照样生成了，`check-package` 也过，
只有浏览器控制台一句 `import failed`。而且因为 DSH 的 client 启动是**全或无**（D1 同源），
症状是整个界面不渲染 —— 看起来像"插件把宿主搞挂了"。

**⇒ 两道防线（都已落地，别再退回去）**：

1. **契约包产出两态**：`lib/`（ESM，给 host）+ `lib-cjs/`（CJS，给 client 内联）。
   见 `packages/contract/tsconfig.cjs.json`。`tools/build.mjs` 两个都跑。
2. **`build-client.mjs` 的 ESM 残留闸门**：任一模块体行首出现 `export` / `import` 就 **exit 1**，
   并直接说明修法。★ 这条闸门**实测过会失败**（把 `lib-cjs` 挪走后确实报错并指到
   `@shanhai/kaipu-contract/index.js:15  export * from './generated.js'`）。

**配套判据**（`check-package.mjs` A3）也改成了**正向**断言：
「插件自身产物若在运行时引用了内部包，bundle 里就必须含有它的内联模块」。
—— 老版本断言的是"产物里不出现 `@shanhai/kaipu-contract`"，加了内联之后它变成**假阳性**
（字符串出现在模块注释里）。**教训：「没有某个字符串」证明不了因果关系。**

### D5 · ★★ 界面探针的三条纪律（2026-10-05，一天之内被打到两次）

界面判据（`tools/probe/*.mjs`）比静态判据脆，因为它跑在一个**有状态的页面**上。
今天连改两轮界面，探针连报"失败"，两次都不是产品坏了，而是探针自己不成立：

| # | 纪律 | 当天怎么被打到的 |
|:-:|:--|:--|
| **D5-a** | ★ **判据必须可复跑** —— 不许假定前态 | `run-view-probe` 第①段假定"刚打开面板 = 默认选中第一个场景"。第一遍通过；第二遍面板还停在上一次跑完的场景 ⇒ **7 条断言误报**。修法：显式 `pickScene('开铺审计 · 标准')`。`copy-probe` 的约束② 同理（变更记录按场景取，不选场景就读到空） |
| **D5-b** | ★★ **断言要读「判据边界」区域，不读整页** | 首屏引导卡里有四类判定的**图例**（它必须在那儿）。若 R3 断言读 `body.innerText`，图例就让「运行视图里出现了 ⚡有条件」**恒真** ⇒ 空断言。修法：运行视图加 `data-kaipu-run`，断言只读它；**并且给这条边界加了自证断言**（`!runText.includes('第一次用？')`），实测把它挪进去会精确报 1 项未过 |
| **D5-c** | **探针对象每次重建**，不做"注入过就跳过" | 改了探针加了 `setIntro()`，页面里还是上一版对象 ⇒ `setIntro is not a function`（不是断言失败，是**崩溃**） |

★ 三条同一个病根：**判据要能被证伪，而不是"跑起来不报错"**。
D5-b 尤其危险 —— 它不会失败，只会**悄悄变成永远通过**。

### D6 · 字号要收成阶梯，不要各处写死（2026-10-05）

面板里原本散着 10 / 11 / 12 / 13 / 14 五个字号，实测反馈是"**字体有点小、第一眼不知道怎么用**"。
根因不是某一处写小了，而是**没有阶梯** ⇒ 想整体调大就得满文件找数字，必然漏几处。

⇒ `theme.ts` 导出 `FS`（`tag 12 / small 13 / base 14 / title 15 / heading 17`）与 `LH`。

★ 顺带一条：字号放大后**左栏宽度与折叠阈值必须一起动**（240→260 / 560→640）。
只改字号不改宽度，症状是"看起来够宽，但左栏每行都挤成两行"。

### D10 · ★ 第三方插件的 `order` 要**排在宿主内置项之后**（2026-10-05 用户实测反馈）

**症状**（阿开报的）：**一刷新，我们的插件按钮就跑到最上面**。

**根因**（宿主源码 + CDP 实测双证）：

```ts
// packages/client/ui-sidebar/src/client/index.ts:50
.sort((a, b) => a.order - b.order)     // 升序；**同值看注册顺序**
```

宿主内置项的 order 区间：`ui-plugin-manager`（插件）**0** · `ui-schedule`（任务）10 · `ui-agent-preset` 20。
**我们原来写的是 `order: 0`** ⇒ 与「插件」同值 ⇒ 实测排到了它**前面**：

```
修前：… 全局面板 · 开铺 · 开铺 · 插件 · 智囊团 …
修后：… 全局面板 · 插件 · 开铺 · 开铺 · 智囊团 …
```

**纪律**：**第三方插件一律取 `> 20` 的值**（我们定 **30 / 35**，留空隙给后来者）。
**理由不是审美**：插件按钮是宿主自带的，**用户已有肌肉记忆**；插到它前面 = **替宿主改布局**。

★ 附带一条：改一个插件的 order 要**回头看同一套插件的其它包** ——
`plugin-wisdom` 原本 `order: 10`（注释写着"排在场地 order 0 之后"），场地改 30 后它就**反超**了。
**"相对顺序"是成套的，不是单点的。**

**判据**：`node tools/check-panel-order.mjs`
断言两条：① 每个插件 `order > 20`（宿主机内置区间上界）② 我们自己的两个 order **不许同值**（同值 ⇒ 顺序看注册运气）。
★ **已做负例验证**：把 `order` 改回 `0` ⇒ 判据精确报 1 项未过、`exit=1`。

### 三个只有逐行读官方源码才知道的结论

**① ★ 我们自造了 3 个字段，DSH 一个都不读。**
`dsh.dshRange` / `dsh.hostApiRange` / `dsh.permissions` —— 全仓零引用。DSH **只读** `dsh.bundle` / `dsh.client` / `dsh.profile`。
已全部移到 `kaipu.*` 命名空间，并删掉 `hostApiRange`（它命名的是一条**不存在的版本轴**：没有独立于 DSH 的"宿主 API 版本"，客户端插槽 API 随 DSH 一起发版）。
`tools/check-market-ready.mjs` 立了护栏：**再往 `dsh.*` 塞自造键就 FAIL**。
理由抄自官方自己的话：*「一个没人读的字段仍然对打开文件的人显得权威……拒绝这个键，才是让文件对它做的事保持诚实的方式。」*

**② ★ 官方的兼容闸门只认 `peerDependencies` 里名字为 `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` 的项 —— 对我们永远放行。**
我们不 import 任何 `dsh-*` 包（与官方 UI 插件同构：注入的包放 `devDependencies`，peer 只留 cordis），所以**分发侧目前没有官方兼容闸门**。
将来 Step 6 对接服务端会 import `dsh-api-*`，**那时必须同步补 peer** —— 官方闸门才真正生效。

**③ ★ `github:` 路线对我们不适用，投稿件必须写 `tarball`。**
