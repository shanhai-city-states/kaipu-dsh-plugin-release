# 坑库 · Agent 密钥轮换 = 对 Agent 断线（2026-10-26）

> **一句话**：`rotate` 把 secret 明文**只回一次**，而这唯一一次没有人的管道去接，
> ⇒ Agent 手里还是旧密钥 ⇒ 之后每次调用都是 `401 验签失败`，**它自己永远修不好**。
>
> 本坑由 2026-10-26 Codex（`codex-caishui-20261024`）真实事故沉淀。

---

## 一、现象（**极易误判的一组**）

| 表面现象 | 实际含义 | 会把人带偏的方向 |
|:--|:--|:--|
| Codex 报「领取任务 401 验签失败」 | 它手里 secret 已作废 | 去查签名格式、查 IP、查服务健康 |
| `/health` 200、其他 GET 都 200 | 服务没问题，只**这一族**签名错 | 「服务抽风」「网络问题」 |
| 换台机器 curl 同一接口 200 | 服务端没问题 | 「Codex 写法不对」→ 让它改代码 |
| `agent_credentials.status = active` | 状态正常**不代表密钥可用** | 「凭据没吊销，肯定不是密钥问题」 |

★ **最后一条最坑**：`active` 只说明「没被吊销」，`rotated_at` 才说明「密钥被换过」。
**只看 `status` 永远查不出来。**

---

## 二、根因（结构性，不是操作失误）

`POST /agents/{id}/rotate` 的契约：

```
rotate() → 旧 secret 立即失效（覆写 blob）
         → 响应体里带 `agentSecret`（明文），**只此一次，此后不可再取**
```

对**人**没影响：人看到响应，复制走，粘到该粘的地方。

对 **Agent 是死结**：

1. 铺主在工位上点「重置密钥」→ 服务端换密钥、旧密钥作废
2. 响应体的明文 secret 落在**铺主浏览器的对话框里**
3. Agent 在**另一台机器**上跑（Codex 在阿舟 Windows，`112.49.211.202`）
4. ⇒ 明文没有通道到达 Agent，**这把新密钥谁也不知道**
5. Agent 继续用旧密钥签名 ⇒ 服务端用新密钥验 ⇒ 永远 401

**时间线实证**（2026-10-26）：

```
04:09:43  rotate  → codex-caishui-20261024.rotated_at 被更新
04:09:31  task 1f7fa8db 被 claim（同一次操作的连锁）
之后       Codex 每次 poll → 401「验签失败」
```

## 三、正解 · 分三层

### L1（现在就能做）· 铺主自助诊断，不依赖任何人在线

**症状 → 一条命令查出来**：

```bash
# 看这把密钥最后什么时候被换过
sqlite3 /opt/shanhai-toolkit-opensource/modules/08-workshop/kai-pu/data/kai_pu.db \
  "select agent_id,status,created_at,rotated_at from agent_credentials
   where account_id='<ACCOUNT_ID>' and status='active';"
```

**判据**：`rotated_at` 晚于 Agent 手上密钥的获取时间 ⇒ **就是这个坑**，不用再查别的。

**修法（铺主自己在工位上就能完成）**：重置密钥 → **把新 secret 亲手给 Agent**。
> ★ 关键动作是「亲手给」，不是「重置」。**只重置不给 = 制造故障。**

### L2（该做的机制）· 让 Agent 能自己活过来

> **★ 乙案已落地（2026-10-26）**：`rotate` 不再让旧密钥立即失效，
> **旧密钥 24 小时内仍可验签**（`prev_blob` + `prev_expires_at`）。
> ⇒ 铺主换密钥后忘了投递，Agent **不会断线**，最多 24h 内补交即可。
> 判据：`tools/judges/check-grace-083.py`（17 项）+ `inject-grace-083.py`（4 项注入）。

现在 Agent **没有**自助恢复通道。三种做法：

| 方案 | 机制 | 代价 | 状态 |
|:--|:--|:--|:--|
| **甲** | `rotate` 支持 `deliverTo`：密钥直接写进 Agent 指定文件/回调，**人不经手明文** | 要定投递契约（已排 V1.1） | 未做 |
| **乙** | 密钥**不再轮换即作废**：新旧密钥双活一个宽限期（如 24h），Agent 下次连上自动换新 | 要加 `secret_prev` 字段 + 验签双试 | ✅ **已完成** |
| **丙** | 工位里「重置密钥」按钮加**一次性投递**：生成一个仅 Agent 可用的一次性取密钥链接 | 链接本身又是凭据，要防转发 | 可做 |

**乙 是保险，甲 是解药。** 有乙就够了：Agent 断不了线，铺主点什么都不至于把机器搞坏。

★ **乙案的边界（必须知道）**：
- 宽限期 **24h**（`store.GRACE_SECONDS`），不是永久 —— 泄露后 24h 内收得住
- **吊销仍然立即生效**，新旧密钥全拒（安全底线不被宽限期削弱）
- 宽限期过了，旧密钥**自动失效**，且下次验签时惰性清空 `prev_blob`
- 响应里会明确回 `prevSecretGraceHours: 24` 和 `prevSecretExpiresAt`

### L3（最省事的一条）· **别给不需要轮换的场景轮换**

★ **轮换只该用于「怀疑泄露」**。日常「Agent 连不上」绝大多数**不是密钥问题**，
轮换只会把一个小故障变成一个需要人工搬运的新故障。

**先查这三项，再决定是否轮换**：

1. `signer` 活着吗 —— `systemctl is-active kai-pu-signer.service`
   （signer 挂了，**全体** Agent 都是 401，此时轮换毫无用处，反而报废全员密钥）
2. 签名放对位置了吗 —— `/agent/*` 族签名在 **JSON body**，不在 HTTP 头
3. `rotated_at` 是否晚于 Agent 上次成功调用的时间

## 四、判据（防止这个坑再出现在代码里）

| # | 判据 | 为什么 |
|:--|:--|:--|
| R-1 | `rotate` 响应**必须**带 `secretNote` 说明「旧密钥已立即失效」 | 让操作人当场知道后果 |
| R-2 | 工位「重置密钥」按钮**不得**在无投递能力时静默成功 | 否则等于悄悄剪断 Agent 的线 |
| R-3 | `agent_credentials` 必须有 `rotated_at`，且**诊断路径读它**（不读 `status`） | `status=active` 无法暴露本坑 |
| R-4 | `signer` 不可用 ⇒ **503 `signer_unavailable`**，绝不报 401 | 已有实现（`gateway.py _agent_self_prove`），勿回退 |

★ R-4 是**已经做过**的正确设计，本坑再证它必要：
**「密钥错」和「服务不可用」混成同一个 401，会把人带偏三轮。**

## 五、铺主自查清单（贴到工位文档里）

> **Agent 报「验签失败 / 401」时，按顺序做这四步，不需要找人：**

1. **看服务**：`curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3560/health` → 非 200 先修服务
2. **看 signer**：`systemctl is-active kai-pu-signer.service` → 非 active ⇒ 重启 signer（**别碰密钥**）
3. **看密钥换过没**：查 `rotated_at` 是否晚于 Agent 上次正常时间 → 是 ⇒ 走第 4 步
4. **重置并投递**：重置密钥 + **把新 secret 交给 Agent**（这一步不做完，故障不会消失）
