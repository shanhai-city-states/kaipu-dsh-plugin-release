## 一、改名类（横切概念）

### 坑 1：改中文名会静默废掉「按名字判断」的判据
- **现象**：`签名位` → `山海顾问位` 一改，全仓 6 处 `name.includes('签名')` 全部失效。
- **后果不是报错，是静默放开**：签名位卡片重新长出邀请按钮；点了发出去的是执行位码
  （2026-10-24 已发生过一次同类事故）。
- **正解**：判据收敛到**一处** `isAdvisorSeat(seatKey, name)`：
  - ① `seatKey` 有值 ⇒ **它定案，名字一个字都不看**
  - ② `seatKey` 为空（老数据）⇒ 退回名字，**新旧名字都认**
  - ③ 兜底：名字含「签名」也认（宁可锁上，不可放开）
- **判据**：`check-seat-summary-083` S-3b~S-3j（10 条），注入 5/5 全抓。

### 坑 2：`if (key === 'signature') return true` 让名字能带偏别的座位
- **现象**：`isAdvisorSeat('execution', '山海顾问位')` 返回 `true`。
- **后果**：一个执行位只要被改名成「山海顾问位」，它的邀请按钮就消失（被误锁）。
- **根因**：key 不匹配时**继续走名字兜底**，等于「名字 > key」。
- **正解**：`if (key !== '') return key === 'signature'` —— **有 key 就信 key，不往下走**。
- **这条是判据 S-3f 抓出来的**（写判据时我以为它是 bug，实际是判据先对了）。

### 坑 3：`ALTER TABLE` 不会改 `CREATE TABLE` 语句
- **现象**：手工 `ALTER` 加了 `pack_files.node_id`，老库能用了。
- **隐患**：**新铺子建表时仍然没有这个字段** —— 全新部署直接坏。
- **正解**：两处都改 —— `SCHEMA` 常量里加列 + `_migrate_xxx()` 里 `ALTER`。

## 二、判据类（同一个族，现在已经第 5 次复现）

| 层 | 错误形态 | 正解 |
|:--|:--|:--|
| 1 | 全文 `includes` | 按**结构边界**切片 |
| 2 | 固定字符数切片 | 数标记 / 找收尾闭合符 |
| 3 | 不剥注释 | 剥块注释 + 行注释 |
| 4 | **验字符串存在** | 验**执行形态**（不被 `false &&` 短路） |
| 5 | **反向断言太粗** | 反向也用结构形态（`>\s*\{p\}` 而非 `\{\s*p\s*\}`） |
| 6 | **判据等价于永远为真** | 见坑 4 |

### 坑 4：`flag_bits & 0x800` 这条判据永远为真
- **现象**：把 `zi.flag_bits |= 0x800` 删掉，判据**仍然全绿**。
- **根因**：Python `zipfile` 在写**字符串**文件名时**自动**打 0x800 ⇒ 结果永远成立。
- **正解**：验**源码里有没有显式设**（`inspect.getsource` + 字符串匹配），
  或验「写的是 `ZipInfo` 对象」这个事实。

### 坑 5：用 `splitlines()` 数 CSV 行数 ⇒ 假红
- **现象**：2 个任务的清单数出 5 行。
- **根因**：「正文内容」列里有真实换行，被 CSV 引号包住了。
- **正解**：用 `csv.reader` 数**记录数**，不能数字符流里的换行。

## 三、真跑类（`py_compile` 抓不到）

### 坑 6：`sqlite3.Row` 没有 `.get()`
- **现象**：`AttributeError: 'sqlite3.Row' object has no attribute 'get'`。
- **根因**：`store.q()` 返回 `sqlite3.Row`，代码当 dict 用。
- **`py_compile` 完全看不出来**（语法是对的）。
- **正解**：统一走 `_row_get(row, key, default)` 兼容两种类型。
- **教训重申**：**编译通过 ≠ 能跑**。本轮 3 个错（Row.get、`re` 未 import、`_safe_slug` 不存在）
  全是真跑抓到的。

### 坑 7：测试脚本自己写错了路径 ⇒ 误判成代码 bug
- **现象**：`pack_files` 有 92 条，导出包附件却是 0。
- **根因**：测试脚本 `root` 拼成 `<repo>/packs`，真实路径是 `/var/lib/kai-pu/packs`。
- **教训**：**「导出没数据」先查自己传的 root，别急着改代码。**

## 四、数据语义类

### 坑 8：别用「现在的状态」改写「历史记录」
- **现象**：`azhou2` 现在是执行位（seq 6），但它 10-23 传的文件记的是 `management`。
  导出成 `04-管理位-azhou2`，看着像 bug。
- **真相**：**那是上传那一刻的事实**。改成 `06-执行位` 才是错的 ——
  等于用今天的状态改写昨天的记录。
- **判据（单一规则）**：
  - `node_id` 有值（新上传才记）⇒ 用它（能区分同类型多工位）
  - `node_id` 为空（存量）⇒ 用 `pack_files.seat`（上传时刻的座位）
  - **两者不交叉**：有 node_id 就不被 agent 当前 lamp 覆盖

### 坑 9：计数口径不一致，客户一眼对不上
- **现象**：包内 7 个文件，清单只有 5 行。
- **根因**：`n` 把 `需求.md`（为每个任务生成的说明）也算进「文件数」，
  但 `manifest.files` 只记业务文件。
- **正解**：`n` = **业务文件**（附件+交付物）；`需求.md` 单列 `generatedDocs`；
  这样「包内总条目 = files + generatedDocs + 4」可对数（判据 E-8b2 盯着）。

### 坑 10：孤儿件（磁盘有、索引无）不能丢
- **现象**：`127-星月-派单...md` 在磁盘上，`pack_files` 里没记录。
- **正解**：**照样进包**（完整性优先于归类），清单里如实写「（未登记）」，
  **不编造上传人/上传时间**（编造 = 给客户假信息）。

## 五、发版链路

### 坑 11：`/plugin/version` 不随包自动更新
- **现象**：发了 v0.2.105 release，服务仍报 `latest: 0.2.104`。
- **根因**：`data/plugin-version.json` 是**独立文件**，发版脚本不管它。
- **正解**：发版三件一起做 —— **① 打包含新版本号 ② 传 release 资产 ③ 改 `plugin-version.json`**。
